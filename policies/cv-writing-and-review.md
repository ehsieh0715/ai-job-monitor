# CV Writing and Review

Version: 1.8.

## Evidence and wording

- Compose from current Profile and reviewed projects. No Master CV is required; consult old CVs only for expression, not extra corroboration.
- Select cases against core JD requirements; avoid similar cases crowding out other important evidence. Prioritize relevant work and results, then projects. Preserve dates, role context, contribution and limits; do not disguise structural gaps. Education or projects may move up when they establish eligibility or a technical transition.
- Describe the owned action, its method or context, and the supported result or purpose. One bullet has a main goal, not an exclusive skill; combine requirements, measurement, collaboration, documentation and validation when they form one supported workflow. CAR is a check, not a mandatory three-part sentence. Do not invent promotions, authority or metrics.
- Start bullets with actions, not routine bold category labels followed by colons. Skill-category labels remain appropriate in Technical Skills.
- Keep technologies that explain implementation or a material JD requirement. Several tools in one coherent workflow are valid evidence; do not remove specificity merely because there are many tools.
- Skills can appear in the index and relevant work; remove mechanical repetition, not implementation evidence. Avoid tool count, "complex" adjectives and generic soft skills as substitutes for scope or results.
- Quantify only supported time, scale, frequency, adoption or outcomes. No metric quota, invented percentages, extrapolated impact or unsupported "significant" claims.
- Use readable approximate scale when exact counts add no value; preserve precise sources in Profile. "Approximately 10 million" cannot become "over 10 million" or production throughput.
- Explain unfamiliar products by intended user and function or supported product count and context; retain employer names. Do not invent features or expect a brand name to explain the product.

## Summary and skills

- Include summary when useful, normally 2–3 sentences and 45–70 words; no duplicate unlabelled introduction.
- Use a compact, grouped hard-skill index with official names and supporting work or project evidence. Keep platform minutiae only when relevant; follow private display preferences.
- Use truthful JD terms naturally. Parsing, recruiter search and human judgment differ; no universal ATS score, keyword density or repetition quota guarantees acceptance.
- Keep standard sections, selectable text and logical order for contacts, employers, roles, dates and degrees. Check actual exported text and parser-populated fields when available; do not claim an employer's unknown ATS configuration.

## Presentation and scope

- Read the saved CV if one exists, private preferences, `templates/README.md` and `templates/CV.md`. The CSS and template provide optional layout defaults, not hiring standards.
- **Priority:** apply employer and current instructions, then private preferences, then template defaults. None weaken factual boundaries.
- **Personal facts:** get facts and GPA scales from Profile, not templates.
- Ireland and UK default: at most two pages and city/country contact details. Omit photos, age, marital status, street address and unsolicited references; include verified work permission only when useful. Follow other employer or market requirements.
- Use single-column selectable text, not layout tables, text boxes, icons or graphics; prioritize content over tiny fonts. Verify reading order rather than promise ATS acceptance.
- Preserve template class names and truthful role, academic, team and portfolio context. Replace placeholders only with supported facts; omit unavailable fields, links and separators.
- **Content source:** maintain CV.md without a second manually edited JSON copy.
- **Layout:** CSS controls appearance; adjust manual page breaks per document.
- **Synchronization:** repo and installed CSS are separate copies; they do not update each other automatically.
- Install or synchronize CSS only when requested, preserving local edits. Layout changes do not authorize text rewrites.
- Preserve approved wording unless correction or material improvement is needed. Comparison questions ask for advice, not edits. Explain material revisions as Current / Proposed / Reason; omit trivial diffs.

## Save and deliver

- Follow workflow for authorization, fixed application paths and preparation dates, version preservation and separate tracker scope. No extra JD, progress or index notes by default.
- CV work does not authorize changes to Sheets, queues, code or policies. PDF export follows its own fidelity, naming and verification rules; it cannot rewrite approved text.
- **Evidence check:** verify JD relevance, personal ownership, metrics and useful technical detail. When shortening or replacing cases, retain required implementation and problem-solving evidence, including validation, investigation, correction and recovery where relevant.
- **Presentation check:** verify template format, dates, links and GPA against private preferences and Profile.
- **Delivery check:** verify the output version; disclose missing source or layout checks.
- **Drafting:** return a short positioning rationale, complete Markdown and saved path.
- **Review only:** return material corrections and open verification questions, not a full rewrite or invented match score.
