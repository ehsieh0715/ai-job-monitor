# CV writing and review

Version: 1.0. Read `evidence.md` and the current job assessment first.

## Content selection

Assess the current JD under evaluation.md first; its questions and drafting
gate and workflow.md's interactive continuation apply. Once drafting is authorized, compose the CV from Candidate Profile and its relevant
verified project sections for the JD. No Master CV, existing CV or single base
version is required. Consult relevant old CVs for useful expression only; do not
read every version by default or treat their repetition as evidence.

Prioritize the strongest relevant responsibilities and results, then supporting
projects. Preserve precise role dates/titles and collaborative boundaries.
Choose section order by evidence; education may move up for graduate eligibility,
projects for a technical pivot. Do not rewrite accurate useful text for novelty.
If revising a supplied CV, use Current / Proposed / Reason only for material edits.

## Wording

Use precise owned action → method/tools/context → verified result or downstream
value. CAR is a diagnostic, not a requirement to force three clauses into every
bullet. Lead with the delivered solution rather than a tool list. Prefer direct
verbs over vague Worked with/Helped/Responsible for when the specific action is
known. Collaboration verbs remain valid with a clear contribution; Led, Owned
and Architected require supporting authority. Vary verbs only for accuracy.

Perform a quantification pass against verified sources: time, scale, frequency,
adoption, tests/model results or business outcomes. No metric quota, invented
percentages, extrapolation or unsupported 'significant' impact. Concrete scope,
method, decision support and downstream use are valid without numbers.

Summary when useful: normally 2–3 sentences, 45–70 words, relevant identity and
strong evidence first. Omit generic enthusiasm and unsubstantiated expertise.
Skills: compact, evidence-supported hard-skill index using official names and
readable groups (e.g. Python (pandas), Power BI (DAX)). Avoid flat component dumps
and generic soft-skill lists; show those traits through achievements. Core skills
need visible supporting experience/project evidence. Detailed platform components
belong in relevant project bullets unless independently important to the JD.
Use supported JD terms naturally, never keyword stuffing.

## Format and delivery

Follow the target market/employer. For Ireland/UK roles normally use up to two
pages, city/country, no photo, age, marital status, full street address or unsolicited
references; include work authorization only when helpful and verified. Other
markets/user preferences can differ. Default generated documents to single-column layout, standard headings, ordinary
links and selectable body-text contact details. Avoid layout tables, text boxes,
icons and graphics; verify actual reading order rather than promising ATS success. Prefer content prioritization over tiny fonts.

Return a concise positioning rationale and the complete Markdown CV; apply
the review checklist below before delivery. Ask about ambiguous company/title/start date.
Do not alter Google Sheets, queues, program files or shared policies as a side effect.

Draft Markdown first. Save only when requested/authorized, to the fixed
<career.root>/applications/Company Name/YYYY-MM-DD - Job Title/CV.md. Folder date is the
preparation start date; actual application date belongs in the tracker. Export
PDF when requested/needed for submission; honor employer format requirements.
Do not create JD, analysis, progress or index notes by default. Preserve submitted
versions; if revising after submission, use an explicitly separate draft/version.
Create/update <career.root>/applications.md only when requested or already authorized;
do not guess dates, NofD or status.

Create needed application directories within authorized scope using the fixed
layout and safe naming rules in workflow.md; users do not configure these paths.

PDF conversion, colour, content fidelity and filenames are owned by pdf.md.

## Review before delivery

Check:

1. The content addresses the actual JD's most important work and preserves the
   fit assessment; prose cannot erase a structural or eligibility gap.
2. Facts, dates, titles, metrics, completion and personal ownership have sources.
   Project/academic/learning evidence is visibly distinct from professional work.
3. Summary and section order support the positioning; bullets identify action,
   method and value without invented impact. Recover relevant verified metrics.
4. Skills are supported, correctly named and readable; important JD terminology
   is natural, with no generic filler or unnecessary component lists.
5. Keep strong content; remove repetition before changing layout/font size.
6. Markdown links and rendering are readable. For exported files inspect page
   layout and text extraction; never claim PDF/ATS validation without doing it.
7. The intended output path is correct and cannot overwrite a submitted version.

For review-only requests, return only material corrections and unresolved
verification questions. For drafting, deliver the complete CV as specified above. Supply
complete replacement sections when useful, not a compulsory long checklist or
arbitrary resume 'match score'. Mark work needing source or layout verification
rather than claiming it passed.

For PDF exports also apply pdf.md; do not rewrite source during conversion.
